# PLAN_2026_05_13_008

## Requirements / Problem

Create two new skills and update one existing skill to support architecture evaluation and improvement as a formal workflow path:

1. **evaluate-architecture** — scans the codebase against best practices, produces a prioritized list of structural issues
2. **improve-architecture** — implements the listed improvements with TDD (existing test or write new one), using `[ARCH]` flags
3. **review-implementation update** — add Step 6.5 (Architecture Integrity Check), update exit texts to offer the new path

These slot into the workflow after `review-implementation` (1st pass), alongside `modularize-and-clean`:

```
review-implementation (1st pass)
    ├──→ modularize-and-clean → review-implementation (2nd pass)
    │     Quick cleanup: fix imports, extract shared code, rename within structure
    │
    └──→ evaluate-architecture → improve-architecture → review-implementation (architecture pass)
          Structural changes: move directories, reorganize packages, relocate assets
```

## Solution

### New Skill: evaluate-architecture (Plan mode, read-only)

- Scans project file tree, ARCHITECTURE.md, PROJECT_BEST_PRACTICES.md, and spot-checks source files
- Checks: directory organization, import hygiene, config placement, asset location, test structure, monolithic patterns, dead/deprecated code, naming conventions
- Outputs a **verbal prioritized list** (P0-P2) with file:line references — no persistent document (same pattern as analyze-and-plan)
- If zero issues found: reports "codebase is clean" and exits without routing

### New Skill: improve-architecture (Build mode)

- Input: verbal list from evaluate-architecture (session context)
- For each item: TDD (existing test or write regression test) → apply structural change with `[ARCH]` flag → verify
- Cross-references implement-plan §3 (batch rules), §5 (surgical changes), §6 (flag format), test-adaptation rule — no duplication
- On stale evaluation list: re-evaluate codebase before acting
- On partial completion: pick up where left off
- On test failure: review if change is logically sound; if safe → keep; if risk → skip and report

### Update: review-implementation

- Add **Step 6.5 Architecture Integrity Check** (conditional — only when prior step was improve-architecture):
  - Verify evaluation list items are fully addressed (no partial-done items missed)
  - Verify no double-paths (file exists in old AND new location)
  - Verify no orphaned references
  - Verify file-level description headers on moved/changed files match convention
- Update exit declarations to offer both paths

### Approach & Design Decisions

- **evaluate-architecture is verbal output only** — like analyze-and-plan. No persistent document. The list lives in the conversation and feeds directly into improve-architecture.
- **improve-architecture skips check-plan-readiness** — the evaluation list IS the plan. No formal plan document needed for architecture improvements.
- **TDD in improve-architecture** — for each item, first check if an existing test covers the behavior. If yes → record baseline count, apply change, verify same count. If no → write a regression test first. This ensures behavioral safety without requiring new feature tests.
- **Cross-reference, don't duplicate** — improve-architecture references implement-plan's batch rules, flag format, and surgical changes guidelines instead of copying them.
- **evaluate-architecture is not a plan-file-consuming step** — it produces analysis for human readability, not machine consumption. The `check-plan-readiness` step is only for implementation plans.

### Edge Cases

| Case | Resolution |
|------|-----------|
| Empty evaluation list | Report "codebase is clean", no routing |
| Partial completion | improve-architecture tracks done items in-conversation, resumes at next undone item |
| Test failure on architecture change | Review logical soundness of the change. If the change is correct but a test was brittle → fix test. If the change breaks intended behavior → skip the item. |
| Stale evaluation list | improve-architecture re-evaluates the current codebase before acting on each item |
| Conflict with modularize-and-clean | evaluate-architecture scans current state, so each run is independent. Items fixed by modularize-and-clean simply won't appear in a fresh evaluation. |
| Repeated evaluation runs | Verbal supersedes: most recent evaluate-architecture output is the source of truth |

### Testing Strategy (TDD)

- **evaluate-architecture itself**: no tests needed (read-only analysis skill, no code output)
- **improve-architecture**: per-item TDD
  - Has existing test? → Record baseline count → apply [ARCH] change → verify same tests pass with same count
  - No existing test? → Write regression test capturing current behavior → apply [ARCH] change → verify
  - Final batch verification: full test suite (backend 25 + frontend 83 + build + typecheck)
- **review-implementation update**: verify new Step 6.5 appears only when relevant; exit texts correctly offer both paths

### Success Criteria

1. `evaluate-architecture/SKILL.md` created with full scan checklist, Plan-mode conventions, verbal output
2. `improve-architecture/SKILL.md` created with TDD-per-item, `[ARCH]` flags, cross-refs to implement-plan
3. `review-implementation/SKILL.md` has Step 6.5 Architecture Integrity Check added (conditional)
4. Exit texts in review-implementation updated: 1st pass offers both modularize-and-clean AND evaluate-architecture
5. Both new skills follow existing skill conventions (front matter, What I do, Documents to Read, Guidelines, Outputs & Triggers)
6. No duplicated content from implement-plan — cross-referenced via section references

## Grill Outcomes

### Dimension: Assumptions
- **A3** — evaluate-architecture output format: **Verbal list** (like analyze-and-plan). No persistent file.
- **A4** — improve-architecture input: **Reads the verbal list directly**. No check-plan-readiness gate.
- **A5** — evaluate-architecture's lifecycle position: **After review-implementation (1st pass)**, alongside modularize-and-clean. NOT after analyze-and-plan.
- **A6** — User path choice: **Guided by exit declarations**. review-implementation's 1st-pass exit offers both modularize-and-clean and evaluate-architecture.

### Dimension: Edge Cases
- **E1** — Empty evaluation: **Report "no issues found"**, do nothing, no routing.
- **E2** — Partial implementation: **Pick up where left off** — track done items in conversation.
- **E3** — Test failure on architecture change: **Review if the change is logically sound**. If yes, fix the test; if not, skip the item. Don't auto-revert.
- **E4** — Stale evaluation list: **Re-evaluate current codebase** before acting on each item.

### Dimension: Alternatives
- **T1** — Merge into analyze-and-plan: **Rejected** — different lifecycle stage.
- **T2** — Merge into implement-plan: **Rejected** — different testing model, flag type, failure handling.
- **T3** — Single audit-architecture skill: **Rejected** — spans Plan+Build modes, breaks one-mode-per-skill.
- **T4/T5** — Separate skills: **Accepted** — each does one thing; cross-reference shared logic.

### Dimension: Risks
- **R1** — Skill proliferation: **Accepted** (user dismissed).
- **R2** — Overlap with implement-plan: **Resolved** — improve-architecture cross-references implement-plan's batch rules, flag format, surgical changes, and test-adaptation rule. Unique behavior (input source, TDD model, [ARCH] flags, failure review, resume/re-evaluate) is self-contained.
- **R3** — Verbal list lost on context loss: **Accepted** (user dismissed — follows modularize-and-clean session pattern).

### Dimension: Dependencies
- evaluate-architecture reads: file tree, ARCHITECTURE.md (§Project Structure, §Module Descriptions, §Import Structure), PROJECT_BEST_PRACTICES.md, spot-check source files.
- improve-architecture reads: verbal list from evaluate-architecture, AGENTS.md (§File Ownership, §Core Commands), ARCHITECTURE.md, existing tests. Cross-references implement-plan SKILL.md (§3, §5, §6, test-adaptation rule).
- review-implementation update: only affects its own SKILL.md.

### Dimension: Consistency
- Naming follows existing pattern: verb-domain (`evaluate-architecture`, `improve-architecture`).
- Front matter format matches existing skills (name, mode, description).
- improve-architecture sits alongside modularize-and-clean in the workflow — same entry point from review-implementation (1st pass).
- review-implementation's new Step 6.5 is conditional (only when prior step was improve-architecture), not always active.
