# PLAN_2026_05_12_002

## Requirements / Problem

The 5-skill planning-to-implementation workflow (analyze-and-plan → grill-and-refine → plan-readiness → implement-plan → review-implementation) lacks structured connectivity. Each skill is self-contained with no explicit output definition, no trigger for the next step, and no consistent exit declaration. The chain works only because the user manually invokes each skill by name. Additionally, `plan-readiness` has a passive verb — rename to `check-plan-readiness` for active clarity.

Goals:
- Each skill defines what it produces (Output)
- Each skill ends with a consistent exit declaration that signals readiness for the next step
- Each skill's frontmatter description reflects its trigger/exit context
- The plan document is created by exactly one step (check-plan-readiness) and read-only for all others
- review-implementation verifies every item in the plan document against actual code

## Solution

Add a structured `## Outputs & Triggers` section to each of the 5 skill files, update frontmatter descriptions, add internal cross-references cleanup, and rename `plan-readiness/` to `check-plan-readiness/` with directory rename.

### Approach & Design Decisions

- Each skill gets a new `## Outputs & Triggers` section at end of file with Output, Exit Declaration, and Next Step
- Frontmatter `description` fields updated to include output context and trigger info
- `plan-readiness` renamed to `check-plan-readiness` — the verb changes from noun ("plan readiness") to action ("check plan readiness")
- The plan document (`plans/PLAN_*.md`) is created by `check-plan-readiness` only. `implement-plan` reads it as read-only — never modifies it.
- `review-implementation` reads the plan document to verify every planned item is implemented
- Internal stale references (`plan-readiness` → `check-plan-readiness`, `grill-plan` → `grill-and-refine`) updated across all 5 skills
- `grill-and-refine` Phase 3 outputs resolved dimensions as copy-ready code blocks for direct capture into the plan file

## Grill Outcomes

### Dimension: Skill Naming
- Decision: Rename `plan-readiness` to `check-plan-readiness`
- Rationale: Active verb clarifies the step's purpose (checking readiness) vs passive noun
- Impact: Directory rename + all internal cross-references updated

### Dimension: Plan File Ownership
- Decision: `check-plan-readiness` is sole creator/writer of plan files. `implement-plan` reads only.
- Rationale: Single source of truth for the plan document. Prevents corruption or drift.
- Impact: Explicit documentation in both skills' Outputs & Triggers sections

### Dimension: Workflow Scope
- Decision: Keep within 5 steps. No pipeline overview doc. No push-to-git in scope.
- Rationale: Focus on core workflow connectivity first. Can extend later.
- Impact: Eliminates need for PIPELINE.md or cross-references to non-core skills

### Dimension: Review Phase Verification
- Decision: `review-implementation` reads the plan document and checks every item against actual code
- Rationale: Ensures nothing from the plan was skipped or half-implemented
- Impact: Step 4 rewritten to explicitly reference the plan document

### Dimension: Grill Output Format
- Decision: Phase 3 outputs resolved dimensions as copy-ready code blocks
- Rationale: `check-plan-readiness` can paste directly into the plan file without reformatting
- Impact: Phase 3 section rewritten

### Dimension: Exit Declarations
- Decision: Each step has a consistent exit phrase that signals readiness for the next step
- Rationale: Clear handoff boundary. User knows exactly when a step is done and what comes next.
- Impact: Frontmatter descriptions updated; `## Outputs & Triggers` section added
