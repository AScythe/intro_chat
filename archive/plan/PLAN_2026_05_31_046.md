# PLAN_2026_05_31_045

## Problem Statement

Session files exist but are archival-only (explicitly marked "not re-readable"). Two pain points:

1. **Compaction strips context** — OpenCode compresses conversation history when token limits are reached. After compaction, the agent has no way to re-establish what it was doing, what phase it was in, or what decisions were made.
2. **Sub-agent delegation loses history** — When the main agent delegates to a Task tool sub-agent, the sub-agent starts with zero conversation context. Relevant session history must be manually extracted.

The existing save-session skill writes conversations to `docs/sessions/SESSION_*.md` but explicitly states these files "are not re-readable for context restoration." We need to make them strategically re-readable — token-cheap enough that reading a session header is always safe, and triggered only when context recovery is needed.

## Goals & Non-Goals

### Goals

- Add YAML frontmatter header to every session file with: `session`, `date`, `phase`, `goal`, `plan` (conditional), `files` (conditional), `outcome` (conditional), `next_step`, `blockers` (conditional)
- Add a **Session Continuity Check** to Phase 0 of all 5 write-phase skills: brainstorm-and-plan, check-plan-readiness, implement-plan, modularize-and-clean, improve-architecture, review-implementation
- The continuity check reads only the **header** of the most recent session file (~15 lines, ~200 tokens) when context appears stale (< 3 user messages AND session files exist)
- Add **save-session triggers** before hand-off in implement-plan, modularize-and-clean, and improve-architecture (check-plan-readiness and review-implementation already have them)
- Continuity check also triggers on user saying "continue" after compaction
- Sub-agent context: main agent manually extracts relevant lines from session header into Task prompt

### Non-Goals

- No INDEX file — headers are cheap enough to read directly (user confirmed)
- No automated sub-agent context injection — main agent extracts manually (user confirmed)
- No change to session file rotation logic (max 3 in `docs/sessions/`, oldest archived)
- No change to tool result truncation rules
- No behavioral code changes — only skill markdown files and AGENTS.md

## Technical Approach

### 1. Session File Header Format

Add YAML frontmatter to every session file, generated at save time:

```yaml
---
session: 003
date: 2026-05-31
phase: implement-plan
goal: Create save-session skill and migrate plan archive
plan: PLAN_2026_05_31_043.md
files:
  - .opencode/skills/save-session/SKILL.md (new)
  - AGENTS.md (modified)
outcome: All tests pass, builds succeed
next_step: Route to review-implementation
blockers: ~
---
```

Required: `session`, `date`, `phase`, `goal`, `next_step`. Conditional (omitted if not applicable): `plan`, `files`, `outcome`, `blockers`.

**Token cost:** ~15 lines, ~200 tokens — trivially cheap to read once; safe to always read on context recovery.

### 2. Session Continuity Check (shared logic)

Insert at Phase 0 of every write-phase skill:

```
Phase 0: Session Continuity Check
1. Scan docs/sessions/ for SESSION_*.md files
2. If none found: skip, proceed normally
3. If files exist AND current context has < 3 user messages:
   - Find most recent session file (highest NNN)
   - Read offset=1, limit=30 (the YAML header)
   - Report: "Restored context from SESSION_NNN: goal=[...], phase=[...], next_step=[...]"
4. On user "continue" after compaction: same flow, always reads header
```

**Why only < 3 user messages matters:** If the conversation already has 3+ exchanges, the agent has enough context to proceed. The session file would be redundant. This threshold avoids unnecessary reads.

**Why header-only:** Full session files can be 100-500 lines. The header contains all information needed for recovery (goal, phase, next step). Full body is never auto-read.

### Architecture & Design Decisions

**Why header-only reads:** Token efficiency. A session file header is ~15 lines (~200 tokens). A full session file can be 500+ lines. The header contains all resume-relevant fields (goal, phase, next step, blockers). Body details (tool outputs, full exchanges) are rarely needed for context recovery and can be explicitly requested by the user.

**Why < 3 user messages threshold:** Empirically, if the conversation has 3+ exchanges, the agent already has sufficient context about what's happening. Fewer than 3 messages (especially after compaction or on fresh "continue") means the agent needs context restoration. This avoids false positives on well-established conversations.

**Why 5 save triggers (not 3):** The user confirmed "all 5 before handoffs." This means every write-phase skill saves before passing control. This ensures that no matter which phase compaction interrupts, the most recent save is from the current skill.

**YAML frontmatter consistency:** Reuses the `---` delimiter pattern already established by SKILL.md files and PLAN.md files. This makes extraction trivial: read up to the closing `---`.

## Open Questions & Risks

- **Risk: save-session during implement-plan Phase 3 Verify may interrupt flow.** Mitigation: save is blocking but quick (header + append, no LLM calls). Should complete in < 2 seconds.
- **Risk: continuity check on fresh session (no session files) is a no-op.** Mitigation: the check is designed to be silent when no files exist.
- **Risk: user "continue" after compaction but before any session was saved.** Mitigation: if no session files exist, the check reports "No session files found — starting fresh context." This is handled naturally.
- **Edge case: multiple session files in docs/sessions/. Which one to read?** Always read the most recent (highest NNN). Older files may be relevant but the most recent contains the most up-to-date context.
- **No prior plan for brainstorm continuity check:** This is the first time a "continuity check" Phase 0 step is being added. There is no existing pattern to follow. The implementation should standardize the phrasing across all skills for consistency.
