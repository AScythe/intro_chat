# PLAN_2026_06_02_050

## Problem Statement

The OrganizeEventPage currently displays rooms and topics as checkbox+label+remove-button lists. All items are treated identically — every room/topic has a remove button, and there's no concept of "default" vs "user-added" items. The organizer needs:

1. **Default rooms/topics** (Main Hall, Table 1-5, Quiet Corner, Coffee Area for rooms; AI Development, DevOps, Swimming, Anime, Job Seeking, Hiring for topics) to always be visible and never removable — only togglable between selected (solid chip) and unselected (ghost/dimmed chip)
2. **User-added items** to appear as chips that disappear when clicked
3. **Checkbox+label replaced** with chip/pill multi-select UI
4. **Toggle state of defaults** to persist across page reloads

## Goals & Non-Goals

### Goals
- Replace checkbox+label+remove-button with clickable chip/pill UI
- Default items: toggle selected↔unselected (ghost font when unselected, never removable)
- User-added items: appear as chip, disappear when clicked (removed entirely)
- Add input sections stay unchanged
- Default toggle state persists via `selected` DB column
- Backend never deletes default rooms/topics
- Save only sends selected item names (same payload format)
- Frontend blocks save when zero rooms selected

### Non-Goals
- No changes to participant-facing RoomPage
- No changes to HomePage, App.tsx, or E2E flow
- No new API endpoints — only modifying existing GET/PUT /config
- No changes to `get_rooms_for_event()` helper used by RoomPage

## Technical Approach

### Overview

| Component | Current | New |
|-----------|---------|-----|
| Rooms/Topics rendering | Checkbox + Label + Remove button | Clickable chip/pill buttons |
| Default vs user-added | No distinction | API returns `is_default` flag; frontend differentiates behavior |
| Remove behavior | All items have ✕ button | Defaults: no remove. User-added: click to remove |
| Selected state | Not persisted (all start checked) | `selected` column in DB; GET returns it; PUT updates it |
| Save behavior | DELETE all + INSERT sent names | Keep defaults (update selected). Delete/re-insert user-added items only |

### Backend Logic

**GET /config:**
- Query `SELECT id, name, selected FROM rooms WHERE event_id = ?`
- Compute `is_default` by checking if name is in `DEFAULT_ROOMS`
- Same for `event_topics` with `DEFAULT_TOPICS`

**PUT /config:**
- Input: `{rooms: [...selected names...], topics: [...selected names...]}` (same format as current)
- Default rooms: never delete, only update `selected = name in payload ? 1 : 0`
- Non-default rooms: delete if name not in payload; insert if new
- Same for topics
- Defaults identified by name-matching against `DEFAULT_ROOMS` / `DEFAULT_TOPICS`

### Frontend Chip Design

- **Selected chip:** `rounded-full px-4 py-2 bg-primary text-primary-foreground shadow-sm text-sm font-medium`
- **Unselected chip (defaults only):** `rounded-full px-4 py-2 border border-input bg-background text-muted-foreground opacity-50 text-sm font-medium`
- **User-added chip:** Always selected style, click removes entirely
- Layout: `flex flex-wrap gap-2`
- On add: if name matches an existing default, toggle that default instead of creating duplicate

### Architecture & Design Decisions

- **`selected` column** in DB for persistence — simpler than a separate state table; ALTER TABLE with try/except for idempotency
- **Name matching** for `is_default` — no `is_default` column needed; cheap operation on small datasets
- **Separate query** for GET /config — does NOT modify shared `get_rooms_for_event()` used by GET /rooms endpoint
- **Chips as styled `<button>` elements** — Badge component is a `<div>` and not interactive; buttons give us proper keyboard accessibility and click handling
- **Same payload format** for PUT — no schema change; backend handles the logic of preserving defaults

## Open Questions & Risks

- **Risk: Race condition on PUT /config** — Two organizers saving simultaneously could cause lost updates. SQLite serializes writes, so no data corruption. Oldest write wins.
- **Risk: Default-name collision** — If a user manually added a room named "Main Hall" before this change, it becomes a default post-migration (name matches). Acceptable.
- **Edge case: Organizer unchecks all defaults** — Frontend blocks save with toast. Backend also validates. Organizer must check at least one default or add a custom room.
- **Edge case: Zero user-added rooms** — Only defaults shown. No empty state needed.

## Grill Outcomes

### Dimension: Assumptions
- Decision: If user types a default name in Add input (e.g., "Main Hall"), toggle that default chip instead of creating a duplicate
- Rationale: Clearer UX, no duplicate confusion
- Impact: Frontend addRoom/addTopic must check existing names before creating new item

### Dimension: Edge Cases
- Decision: Frontend blocks save if no rooms selected (toast + early return). Backend still validates as secondary guard.
- Impact: handleSave checks `selectedRooms.length === 0` before making API call
- Migration: Set `selected=0` for all existing rooms/topics via UPDATE, then set defaults back to `selected=1`

### Dimension: Alternatives
- Decision: Persist toggle state via `selected` column in DB (not session-only)
- Rationale: Organizer's choices remembered across page reloads
- Impact: DB migration with ALTER TABLE + UPDATE statements

### Dimension: Dependencies
- Decision: GET /config uses its own query (NOT modify shared `get_rooms_for_event`); GET /rooms endpoint unchanged
- Rationale: Clean separation; RoomPage doesn't need `selected`
- Impact: Two separate query paths instead of a shared function

### Dimension: Risks
- Decision: Backend identifies default items by name-matching against `DEFAULT_ROOMS` / `DEFAULT_TOPICS` on save
- Rationale: No new column needed; organizer-named "Main Hall" treated as default (acceptable)
- Impact: PUT /config compares payload names against config constants

### Dimension: Consistency
- Decision: Chip UI uses styled `<button>` elements (not Badge component)
- Rationale: Badge is a `<div>` and not interactive; buttons give keyboard accessibility
- Impact: Custom styling matches app patterns

- No missed files or communities found. OrganizeEventPage is only imported by App.tsx and linked from HomePage.tsx. The config endpoint is only used by OrganizeEventPage. Blast radius is contained to 5 source files + 2 test files.
