# PLAN_2026_06_09_002

## Problem Statement

`POST /api/events` currently returns **409 Conflict** when an event with a duplicate name exists. The user wants **cascade-and-replace** behavior instead: delete the old event + all associated child data (rooms, users, matches, interests, sample_users, topics), then create the new event. This allows re-creating events with the same name without manual cleanup.

Separately, the **grill-and-refine** skill needs a process improvement: during grilling, the agent should classify dimensions as critical (needs user discussion) vs non-critical (agent decides using best practices and project logic), then show all decisions at the end for final confirmation.

## Goals & Non-Goals

### Goals
- Replace 409 Conflict with cascade-and-replace in `POST /api/events`
- Wrap INSERT in try/except IntegrityError for race-condition safety (catch → 409 retry)
- Add `test_event_replacement()` verifying old event is gone and new event is intact
- Update `docs/ARCHITECTURE.md` to reflect the new behavior
- Update `.opencode/skills/grill-and-refine/SKILL.md` with critical/non-critical dimension triage process

### Non-Goals
- Not changing `utility/cleanup_db.py` — already has correct cascade logic
- Not changing `app/database.py` — UNIQUE index stays as safety net

## Success Metrics

- Creating event with existing name returns 200 with new `event_id` (not 409)
- Old event_id + all child data is gone from DB (verified via 404 on `/config`)
- New event has 8 fresh default rooms
- Race condition (concurrent POST with same name) returns 409 retry
- Grill-and-refine skill has the new critical/non-critical triage process
- All 20 tests pass (19 existing + 1 new)

## Technical Approach

### Cascade order (must match `cleanup_db.py` and `test_app.py`)

```
room_sample_users → matches → user_interests → users → rooms → event_topics → events
```

### In `routes_api.py`:
1. `SELECT id FROM events WHERE name = ?` to find existing event
2. If found: cascade-delete (fetch room_ids → delete room_sample_users → delete matches → delete user_interests → delete users → delete rooms → delete event_topics → delete event)
3. `INSERT INTO events` with new `id` and same `name`
4. Wrap INSERT in try/except IntegrityError → return 409 on race
5. Call `insert_default_rooms()` and `insert_default_topics()` as before
6. Add `logger.info()` when cascade-delete fires

### In `grill-and-refine` skill:
1. Phase 2, step 1: Classify each dimension as CRITICAL or NON-CRITICAL
2. Phase 2, step 2: User walks through CRITICAL dimensions only
3. Phase 2, new step 3: Agent decides NON-CRITICAL dimensions using best practices and project logic
4. Phase 2, new step 4: Show ALL dimension decisions for final confirmation

### In `test_app.py`:
Create event "Replacement Test" → create again with same name → verify old event gone (404), new event has 8 rooms, event_ids differ.

### Architecture & Design Decisions

- **Cascade order must be consistent** across routes_api.py, cleanup_db.py, and test_app.py
- **No shared function** — the 3 locations use different DB APIs (sync sqlite3 vs async aiosqlite), making extraction over-engineering
- **UNIQUE index stays** — acts as safety net for the race-condition catch
- **try/except IntegrityError** around INSERT handles the rare concurrent-duplicate race

## Open Questions & Risks

- **Race condition:** Two concurrent POST with same name → both pass SELECT, both DELETE, second INSERT hits UNIQUE constraint. Handled via try/except → 409.
- **Data loss:** Cascade-delete is irreversible. Only triggers on explicit user action (POST). All event data is user-created.
- **Old ARCHITECTURE.md:** Already updated in prior plan, may need fresh update.
