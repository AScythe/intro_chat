# PLAN_2026_05_31_032

## Problem Statement

On the profile page (UserInfoPage), after saving the profile, the success state is shown as a separate banner div ("Profile saved! You can now select a room.") rather than integrating into the save button itself. Additionally, there's no way to navigate back to the profile page from downstream pages, and no "Back to Home" button on the profile page.

## Goals & Non-Goals

### Goals
- Save button becomes "Profile saved! Select a room." and disabled after successful save
- Remove the separate success banner
- Editing any form field reverts the button to "Save Profile" and re-enables it
- Select Room button becomes disabled again when form has unsaved changes
- Add "Back to Home" footer button on UserInfoPage
- Add "← Back to Profile" header link on RoomPage
- Add "← Back to Room" header link on PeoplePage
- All tests pass with no regressions

### Non-Goals
- Backend API changes (POST `/api/events/{event_id}/join` stays unchanged)
- Storing original field values for "revert detection" (standard dirty-form behavior)
- Adding back links to ChatPage, ConnectPage, or HomePage (out of scope per user decision)

## Success Metrics

- After save: button text is "Profile saved! Select a room." and `disabled={true}`
- After save: no success banner `<div>` in DOM
- Editing any input (name, LinkedIn, Slack): button text reverts to "Save Profile" and re-enables
- "Back to Home" on UserInfoPage navigates to `/`
- "← Back to Profile" on RoomPage navigates to `/join/:eventId`
- "← Back to Room" on PeoplePage navigates to `/room/:eventId`
- All existing tests pass (93 baseline)
- `npx tsc --noEmit` clean

## Technical Approach

### State logic (UserInfoPage)
- Existing `saved` state doubles as "is saved AND no pending changes" flag
- Each `onChange` handler calls `setSaved(false)` alongside its field setter
- Button render logic:
  - `saving === true` → "Saving...", disabled
  - `saved === true` → "Profile saved! Select a room.", disabled
  - otherwise → "Save Profile", enabled
- Success banner `<div>` removed entirely

### Header back links (RoomPage, PeoplePage)
- `variant="link"` button with `← Back to ...` text, placed above the `<h1>` inside `<header>`
- Uses existing `navigate()` import and `eventId` from `useParams`

### Footer back home (UserInfoPage)
- Matches RoomPage pattern: outline button in `<footer>` with `onClick={() => navigate('/')}`

### Architecture & Design Decisions

- **onChange reset** (not useEffect): simpler, more explicit. Each of 3 inputs gets `setSaved(false)` inline.
- **Header back links** (not footer): follows standard mobile-web pattern for "back to previous page"
- **No new state variables**: `saved` + `saving` are sufficient for all states
- **No new dependencies**: all imports (Button, navigate) already available
