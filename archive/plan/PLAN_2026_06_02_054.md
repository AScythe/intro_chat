# PLAN_2026_06_02_053

## Problem Statement

1. **Chip selection reversal on OrganizeEventPage persists** — clicking a chip to deselect, then typing in the "Add new room"/"Add new topic" input, causes the chip to visually revert to its previous state. The stale-closure fix from Plan 051 is in the source code but the bug is still observed in the running app.
2. **No E2E test for organizer flow** — the existing E2E suite (`userFlow.spec.ts`) only covers participant flow (join, match, chat). Organizer-specific actions (navigate to organize page, configure rooms/topics, save, verify sample users) have zero coverage.
3. **Sample users are static frontend data** — the 21 sample users in `demoData.ts` are keyed by room name and never persist. There is no mechanism to pre-fill rooms with sample users after organizer saves the config, nor a way to verify this end-to-end.
4. **Grill-and-refine skill prompts user to choose dimensions** — the skill's Phase 2 step 1 instructs the agent to ask the user which dimensions to discuss, breaking the flow. The agent should instead identify relevant dimensions and walk through them directly.

## Technical Approach

### Overview

```
Organizer clicks Save on OrganizeEventPage
    ↓
PUT /api/events/{id}/config  (modified: returns rooms_filled)
    ↓
Backend: for each selected room that has 0 entries in room_sample_users,
  pick 3-5 random users from SAMPLE_USERS (at least 1 available),
  insert into room_sample_users table
    ↓
Response: {success: true, rooms_filled: ["Main Hall", "Table 1", ...]}
    ↓
Frontend toast: "Main Hall filled with sample users!" (one per room)
    ↓
Participant joins, visits PeoplePage
    ↓
GET /api/events/{id}/rooms/{rid}/users  (new endpoint)
    ↓
PeoplePage renders sample users from API, falls back to static demoData.ts
```

### Chip Bug Fix Strategy
1. Rebuild frontend `dist/` — the functional updater fix exists in source but may not be in the running build
2. If rebuild doesn't fix it: add React DevTools, trace `rooms` state changes during chip click → input keystroke
3. If root cause found: apply minimal targeted fix in `OrganizeEventPage.tsx`
4. E2E test for chip stability validates the fix

### Sample User Storage
- Backend Python file `app/sample_users.py` defining ~30 users matching existing naming convention (Alex_Coder, Sarah_Dev, etc.)
- Each user has: `name`, `available`, `status`, optional `linkedin_url`, optional `slack_handle`
- Same user can appear in multiple rooms (duplicates allowed across rooms)
- Inserted into `room_sample_users` DB table on save

### Database Schema
New table `room_sample_users`:
```sql
CREATE TABLE IF NOT EXISTS room_sample_users (
    id TEXT PRIMARY KEY,
    room_id TEXT NOT NULL,
    user_name TEXT NOT NULL,
    available INTEGER DEFAULT 0,
    status TEXT DEFAULT '',
    linkedin_url TEXT DEFAULT '',
    slack_handle TEXT DEFAULT '',
    FOREIGN KEY (room_id) REFERENCES rooms (id)
);
```

### Architecture & Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| PeoplePage data source | Backend API | Persistent, E2E-verifiable via HTTP |
| Duplicate users across rooms | Allowed | Simpler, matches real-world events |
| Partial fill failure | Atomic all-or-nothing | Prevents inconsistent state |
| Re-save behavior | Skip if COUNT(*) > 0 | Idempotent, no `filled` flag needed |
| Sample user social data | Some have it, some don't | Realistic mix |
| PersonCard display | Name + status only | Matches real user cards |
| Chip bug fix order | Rebuild first, trace if persists | Fastest path to resolution |

## Open Questions & Risks

- **Chip bug root cause**: If rebuild doesn't fix it, the cause is unknown and needs deeper investigation with React DevTools
- **`Date.now()` as room ID**: Two custom rooms added rapidly could share the same ID, causing React key collisions. Low probability in practice.
- **E2E timeouts**: Adding 4 new E2E tests increases total suite time. The existing 90s timeout per test should be sufficient.
