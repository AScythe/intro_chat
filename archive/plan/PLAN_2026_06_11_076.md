# PLAN_2026_06_11_076

## Problem Statement

On the Find Chat Partners page (PeoplePage), clicking "Request 2-min chat with selected person" does not proceed to the next step. For real-user chat requests, the page stays stuck because:

1. The `match_found` WebSocket event is required to transition from "waiting for response" to the next state
2. But `socket.connect()` is never called on PeoplePage — it's only called in ChatPage
3. The server silently drops WS messages to unconnected users

Additionally, the button text should read "Request chat with selected person" instead of "Request 2-min chat with selected person".

## Goals & Non-Goals

### Goals
- Connect WebSocket on PeoplePage mount so real-user chat requests can receive `match_found` events
- Change button text to "Request chat with selected person"
- Guard against sending requests before WebSocket is connected
- Clean up WebSocket connection when leaving PeoplePage

### Non-Goals
- Not changing the real-user chat request flow backend (already works correctly)
- Not changing sample-user flow (already works via REST API)
- Not changing ChatPage or other pages

## Success Metrics

1. Real-user chat request: click button → WaitingResponseView → match_found WS event received → transitions to match countdown → navigates to chat
2. Button text reads "Request chat with selected person"
3. All existing frontend tests pass

## Technical Approach

Add a `useEffect` in PeoplePage to call `socket.connect(user.userId)` on mount and `socket.disconnect()` on unmount. Add `socket.isConnected` guard to disable the "Request chat" button until WS is ready. Change button text in PeoplePageViews.

### Architecture & Design Decisions

- **WS connection timing**: Connect on mount, disconnect on unmount (matches ChatPage pattern)
- **Null user guard**: Only connect if `user?.userId` exists
- **isConnected guard**: Disable button until `socket.isConnected` is true to prevent sending request without active WS
- No changes to SocketContext, useChatRequest, or backend code
