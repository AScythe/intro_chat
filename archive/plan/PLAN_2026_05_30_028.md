# PLAN_2026_05_30_001

## Problem Statement

The full graph (`graphify-out/graph.json`) contains 1887 nodes across 3 types (code, document, rationale). Querying it for code-specific questions wastes tokens on document nodes (1443, ~76% of the graph). There's no built-in way in graphify to filter queries by `file_type`. We need type-specific sub-graphs that preserve cross-type boundary connections.

## Goals & Non-Goals

### Goals
- Produce `graph-code.json` (code nodes + rationale boundaries) — 444 nodes, 77% fewer than full
- Produce `graph-docs.json` (document nodes only) — 1443 nodes, 24% fewer than full
- Preserve all cross-type edges as full or stub nodes at boundaries
- Zero changes to graphify itself
- CLI-only query (`--graph` flag); MCP server unchanged

### Non-Goals
- No standalone rationale graph (all 36 rationale nodes are already in the code graph as full nodes)
- No MCP server changes
- No graphify source modifications

## Success Metrics

- `graph-code.json` has exactly 444 nodes (408 code + 36 rationale) and 741 edges
- `graph-docs.json` has exactly 1443 nodes and 1387 edges
- `graphify query "python routing" --graph graph-code.json` runs successfully
- All top-level keys (`directed`, `multigraph`, `graph`, `hyperedges`, `built_at_commit`) preserved
- 115/115 agent guidelines tests pass after AGENTS.md edit

## Technical Approach

A standalone Python script (`utility/filter_graph.py`) that:
1. Reads the full `graph.json` with all metadata keys
2. For each requested `file_type`:
   - Collects all nodes of that type (full content)
   - Collects all nodes of other types directly adjacent via edges (as minimal stubs: `{"id", "file_type", "label":""}`)
   - Preserves all edges (both within-type and cross-type)
   - Writes a complete `graph-{type}.json` with identical top-level structure
3. Supports `--all` for batch generation

### Stub Format
```json
{"id": "x", "file_type": "code", "label": ""}
```
~40 bytes vs ~700 bytes for a full node. No `source_file`, `community`, `norm_label` — just enough to hold the edge endpoint.

### Graph Structure (derived from actual data)

| Type | Full Nodes | Stub Nodes | Total | Edges |
|------|-----------|------------|-------|-------|
| code | 408 | 36 (rationale) | 444 | 741 |
| document | 1443 | 0 | 1443 | 1387 |
| Full graph | 1887 | — | 1887 | 2128 |

### Format Preservation
The script copies all top-level keys from source graph.json verbatim (`directed`, `multigraph`, `graph`, `hyperedges`, `built_at_commit`), replacing only `nodes` and `links` arrays. This ensures graphify's `--graph` flag and NetworkX `node_link_graph` parser work on the output.

### Architecture & Design Decisions

- **Rationale nodes as full content** (not stubs) — only 36 nodes, negligible token cost, preserves their content
- **Doc graph has 0 stubs** — documents are isolated from code/rationale in the graph, so doc-graph = doc nodes only
- **CLI-only** — `graphify query --graph <path>`; MCP unchanged
- **Manual rebuild** — agent runs `python utility/filter_graph.py --all` after each graph rebuild
- **Staleness guard** — AGENTS.md instructs agent to check timestamps before querying sub-graphs

## Grill Outcomes

### Dimension: Assumptions
- Decision: Rationale nodes (36) are full content, not stubs, inside the code graph. Doc graph has zero boundaries (doc nodes are isolated).
- Rationale: 36 nodes is negligible for token cost; preserves their content. Graph analysis confirmed zero cross-type edges between code and documents.
- Impact: Code graph = 408 code + 36 rationale = 444 full nodes. Simpler stub logic (stub only needed if a non-target-type node has edges to/from target-type nodes).

### Dimension: Edge Cases
- Decision: Isolated nodes with 0 edges are still included as full nodes (edge case, not an issue in current data). Rationale standalone graph skipped. Graph JSON format (NetworkX `node_link_graph` with `links` key) must be preserved exactly.
- Rationale: The script copies all top-level keys verbatim and replaces only `nodes`/`links`.
- Impact: Script is format-safe; no special handling needed for edge cases.

### Dimension: Alternatives
- Decision: CLI-only (`graphify query --graph <path>`). MCP server unchanged.
- Rationale: Simpler than running multiple MCP servers. CLI query already supports `--graph`.
- Impact: Agent must use CLI query for type-specific questions, MCP for broad architecture.

### Dimension: Dependencies
- Decision: Manual rebuild (`python utility/filter_graph.py --all` after each `graphify update .`/`cluster-only .`).
- Rationale: Consistent with `enhance_graph_viewer.py` workflow. One extra command, no infra changes.
- Impact: AGENTS.md must state the rebuild command clearly.

### Dimension: Risks
- Decision: Staleness is mitigated by timestamp comparison instruction in AGENTS.md.
- Rationale: Simple, practical. The full graph is the source of truth; sub-graphs are derived artifacts.
- Impact: AGENTS.md needs a "staleness guard" instruction.
