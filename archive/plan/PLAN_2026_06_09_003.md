# PLAN_2026_06_09_003

## Problem Statement

The app has **two siloed user storage systems**:

- **`users` table** — real users who join via `POST /api/events/{id}/join`. Has columns: `id`, `event_id`, `room_id`, `username`, `linkedin_url`, `slack_handle`, `is_available`, `created_at`, `last_seen`. Matchable via `matches` table. Has interests via `user_interests`.
- **`room_sample_users` table** — auto-generated sample users created by `PUT /api/events/{id}/config`. Has columns: `id`, `room_id`, `user_name`, `available`, `status`, `linkedin_url`, `slack_handle`. Cannot be matched. Cannot have interests. Not in `store.active_users`.

When a real user (e.g. "alvin") joins an event, picks a sample user, and chats with them:
1. `GET /api/events/{id}/rooms/{rid}/users` returns **only** `room_sample_users` — real users never visible in PeoplePage
2. The `useChatRequest` hook runs **entirely client-side simulation** — no backend API call
3. Chat navigates to `/chat/demo_xxxxx` with a fake `demo_` match ID
4. **No match record is ever created** in the `matches` table
5. **No connection exchange** happens via the real API

## Goals & Non-Goals

### Goals
1. **Unify into one `users` table** — sample users and real users share the same schema with same columns
2. **Real match records** — `matches` table records matches involving sample users
3. **Request-based chat** — "Request 2-min chat" on PeoplePage calls real backend API, creates match records
4. **All users visible** — `GET /api/events/{id}/rooms/{rid}/users` returns both real and sample users
5. **Request-chat for all users** — both sample users (60/40 auto) and real users (WebSocket accept/decline)
6. **Connection exchange for sample users** — backend auto-decides sample user's vote (60/40)
7. **Remove `room_sample_users` table** — clean up all references

### Non-Goals
- Remove `demoData.ts` fallback in frontend (kept for API failure resilience)
- Change `utility/cleanup_db.py` beyond replacing `room_sample_users` references
- Change E2E test Playwright files

## Success Metrics

1. `room_sample_users` table no longer referenced in any Python or TS source code
2. `GET /api/events/{id}/rooms/{rid}/users` returns `users` array with both `is_sample=0` and `is_sample=1` users
3. `POST /api/users/{id}/request-chat` with sample target creates `matches` table record

### Request-Chat Flow

**Sample user target (60/40 auto):**
```
A clicks "Request 2-min chat" on B (sample)
  → POST /api/users/{A_id}/request-chat { target_user_id: B_id }
  → Backend: random 60/40
    → Accept (60%):
      1. persist_match(A, B, room_id) → match_id in matches table
      2. update_match_state: add to active_matches, remove from queue, set is_available=False
      3. Set B's status to "Currently in a chat, find directly in <room>"
      4. Store B's original is_available/status in match.original_user_status
      5. notify_match_found(A) via WebSocket
      6. Return { accepted: true, match_id }
    → Decline (40%):
      1. Return { accepted: false, message: "..." }
  → Frontend:
    → Accepted: viewState='accepted' → ready flow → navigate to /chat/{match_id}
    → Declined: show toast, back to 'showing'
```

**Real user target (WebSocket accept/decline):**
```
A clicks "Request 2-min chat" on B (real)
  → POST /api/users/{A_id}/request-chat { target_user_id: B_id }
  → Backend:
    1. Create PendingRequest(requester_id=A, target_id=B, room_id, ...)
    2. WebSocket 'chat_request' to B { requester_id, requester_name, room_id }
    3. Return { accepted: null, status: 'pending' }
  → Frontend A: viewState='waitingResponse', listen for 'match_found' WS event
  → Frontend B: receive 'chat_request' WS event → show incoming request UI (accept/decline buttons)
    → B accepts → POST /api/users/{B_id}/accept-request { requester_id: A_id }
      → Backend: create match, broadcast 'match_found' to A+B via WS, remove pending request
      → A receives 'match_found' → countdown → chat
      → B receives 'match_found' → countdown → chat
    → B declines → POST /api/users/{B_id}/decline-request { requester_id: A_id }
      → Backend: remove pending request, broadcast 'chat_request_declined' to A
      → A shows declined toast, back to 'showing'
```

### Connection Exchange with Sample Users

When a real user votes on connection exchange, and the match partner is a sample user:

1. Backend checks `match.original_user_status` → if partner has is_sample data
2. Backend auto-generates sample user's vote: `random.random() < 0.6`
3. Both votes exist → broadcast result immediately
4. After result, restore sample user's original `is_available` and `status` (from `match.original_user_status`)
5. Update both in-memory store AND `users` table in DB

### Auto-Matching Exclusion

`find_or_enqueue_match` skips users with `is_sample=1`:
```python
u.get('is_sample', 0)  # Skip sample users
```

### Match Cleanup — Restore Sample Users

`tasks.py::cleanup_expired_matches` restores sample users' original `is_available` and `status` from `match.original_user_status` when the match expires. Updates both in-memory store and `users` table.

### Architecture & Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| `is_sample` flag | INTEGER DEFAULT 0 on `users` table | Distinguishes auto-generated vs real users without separate table |
| Column name: `is_available` | Use existing `users` convention (not `available`) | Consistency with existing codebase |
| Column name: `username` | Use existing `users` convention (not `user_name`) | Consistency |
| Request-chat flow | Backend endpoint + WebSocket | Real match records + accept/decline for real users |
| Sample user auto-acceptance | 60/40 random | User preference for natural feel |
| Sample user connection vote | 60/40 random, backend auto-decides | User preference |
| Client-side readiness simulation | Keep current `setTimeout` flow for sample users | User explicitly chose this over backend-ready flow |
| Test determinism | `force_accept` field in `RequestChatRequest` | Controllable test paths without mocking random |
| Original user status storage | `MatchData.original_user_status` dict | Track sample user's original availability for restore on match end |
| `room_sample_users` removal | `DROP TABLE IF EXISTS` in database.py migration | Clean schema; existing DBs get table dropped on next app start |
| No UNIQUE index on `users(event_id, username)` | Skip it | Two real users can share a name (e.g. "alvin") |
| Fallback for PeoplePage | Keep `demoData.ts` + `useDemoSimulation` | Resilience when API is unavailable |

  ```python
  @router_api.post('/api/users/{user_id}/request-chat')
  async def request_chat(user_id: str, data: RequestChatRequest) -> dict:
      target_id = data.target_user_id
      
      # Validate both users exist
      async with aiosqlite.connect(DB_PATH) as db:
          cursor = await db.execute('SELECT id, event_id, room_id, username, is_sample FROM users WHERE id = ?', (user_id,))
          requester = await cursor.fetchone()
          if not requester:
              raise HTTPException(status_code=404, detail='Requester not found')
          
          cursor = await db.execute('SELECT id, event_id, room_id, username, is_sample FROM users WHERE id = ?', (target_id,))
          target = await cursor.fetchone()
          if not target:
              raise HTTPException(status_code=404, detail='Target not found')
          
          # Same event check
          if requester[1] != target[1]:
              return {'accepted': False, 'message': 'Users are in different events'}
          
          # Same room check
          if requester[2] != target[2]:
              return {'accepted': False, 'message': 'Users are not in the same room'}
          
          # Active match check
          with store.lock:
              for m in store.active_matches.values():
                  if user_id in (m['user1_id'], m['user2_id']):
                      return {'accepted': False, 'message': 'You are already in a chat'}
                  if target_id in (m['user1_id'], m['user2_id']):
                      return {'accepted': False, 'message': 'This person is currently in a chat'}
          
          target_is_sample = bool(target[4])
          
          if target_is_sample:
              import random
              accepted = data.force_accept if data.force_accept is not None else random.random() < 0.6
              if not accepted:
                  return {'accepted': False, 'message': 'declined'}
              
              match_id = await persist_match(user_id, target_id, str(target[2]))
              
              # Store original status in match data (handled by update_match_state)
              update_match_state(match_id, user_id, target_id, str(target[2]))
              
              # Update sample user status in DB
              cursor = await db.execute('SELECT name FROM rooms WHERE id = ?', (target[2],))
              room_name = (await cursor.fetchone())[0]
              new_status = f'Currently in a chat, find directly in {room_name}'
              await db.execute('UPDATE users SET is_available = 0, status = ? WHERE id = ?', (new_status, target_id))
              await db.commit()
              store.update_user(target_id, is_available=False, status=new_status)
              
              await notify_match_found(match_id, user_id, target_id, str(target[2]))
              return {'accepted': True, 'match_id': match_id}
          else:
              # Real user — send WebSocket chat request
              requester_name = str(requester[3])
              target_name = str(target[3])
              
              store.add_pending_request(
                  requester_id=user_id,
                  target_id=target_id,
                  room_id=str(target[2]),
                  requester_name=requester_name,
                  target_name=target_name
              )
              
              await manager.broadcast_to_users(
                  [target_id],
                  {'type': 'chat_request', 'requester_id': user_id, 'requester_name': requester_name, 'room_id': target[2]}
              )
              return {'accepted': None, 'status': 'pending', 'message': 'Chat request sent'}
  ```

  ```python
      pending = store.get_pending_request(data.requester_id)
      if not pending or pending['target_id'] != user_id:
  ```

*Detailed changes (full rewrite):*
```ts
interface PersonResponse {
  accepted: boolean;
  message: string;
  match_id?: string;
}

interface UseChatRequestOptions {
  userId: string;
  eventId: string;
  socket?: { subscribe: <T>(type: string, cb: (data: T) => void) => () => void };
}

export function useChatRequest(options: UseChatRequestOptions) {
  const [requestedPerson, setRequestedPerson] = useState<UserData | null>(null);
  const [personResponse, setPersonResponse] = useState<PersonResponse | null>(null);
  const [yourReady, setYourReady] = useState(false);
  const [theirReady, setTheirReady] = useState(false);
  const [isPending, setIsPending] = useState(false);
  const [error, setError] = useState('');

  const requestChat = useCallback(async (person: UserData) => {
    setRequestedPerson(person);
    setPersonResponse(null);
    setYourReady(false);
    setTheirReady(false);
    setError('');

    // For sample users — simulate readiness client-side
    if (person.is_sample) {
      const resp = await fetchJSON<RequestChatResponse>(`/api/users/${options.userId}/request-chat`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ target_user_id: person.id }),
      });

      if (resp.accepted) {
        setPersonResponse({ accepted: true, message: 'Chat request accepted!', match_id: resp.match_id });
        setTimeout(() => setTheirReady(true), CONFIG.SIMULATE_READY_DELAY_MS);
      } else {
        setPersonResponse({ accepted: false, message: resp.message || 'declined' });
      }
    } else {
      // For real users — send request, wait for WS response
      setIsPending(true);
      try {
        const resp = await fetchJSON<RequestChatResponse>(`/api/users/${options.userId}/request-chat`, {
          method: 'POST',
          headers: { 'Content-Type': 'application/json' },
          body: JSON.stringify({ target_user_id: person.id }),
        });

        if (resp.status === 'pending') {
          // Will receive match_found or chat_request_declined via WS
        }
      } catch {
        setError('Failed to send chat request');
        setIsPending(false);
      }
    }
  }, [options.userId, options.eventId]);

  const imReady = useCallback(() => setYourReady(true), []);
  const cancelRequest = useCallback(() => {
    setRequestedPerson(null);
    setPersonResponse(null);
    setYourReady(false);
    setTheirReady(false);
    setIsPending(false);
    setError('');
  }, []);

  return { requestedPerson, personResponse, yourReady, theirReady, isPending, error, requestChat, imReady, cancelRequest };
}
```

## Open Questions & Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| **Race condition: request-chat + queue toggle** | Both flows fire simultaneously for same user | Don't allow request-chat if user is in waiting queue; reject queue-add if user has pending request |
| **Race condition: two real users request-chat each other simultaneously** | Two pending requests, one overwrites the other | Pending request keyed by requester_id — the second one overwrites the first; use `timeout` cleanup on pending requests (30s expiry) |
| **Frontend WS event missed** | User not on PeoplePage when receiving `chat_request` | Use Sonner toast for global notification; stale request auto-cleans after timeout |
| **Test flakiness from asyncio cleanup** | `cleanup_expired_matches` runs in background thread during tests | Mock the thread in tests; test `find_expired_matches` pure function separately |
| **`demoData.ts` fallback out of sync** | Fallback users don't match backend-generated users | Backend inserts from `SAMPLE_USERS` list directly — `demoData.ts` is a copy that may drift; accept this as minor risk |
| **DB migration on existing databases** | Existing `room_sample_users` data becomes orphaned | `DROP TABLE IF EXISTS` cleans up silently; user chose "start fresh, no migration" |
