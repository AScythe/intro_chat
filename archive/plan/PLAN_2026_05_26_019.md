# PLAN_2026_05_26_002

## Problem Statement

The current E2E test suite (5 scenarios) only verifies that the chat page *loads* — it doesn't simulate the actual user flow through the timed conversation, connection exchange decision, and navigation back to the main menu. This leaves the most important user-facing path (chat → share/decline → home) untested. Additionally, the room used for matching is always `rooms[0]` (Main Hall), missing coverage of other rooms.

## Goals & Non-Goals

### Goals
- Add 2 new E2E tests that cover the full post-match chat lifecycle from timer expiration through connection decision through navigation home
- Test both connection paths: both users connect ("Connection Exchanged!") and one declines ("Chat Complete")
- Use Playwright `page.clock.fastForward()` to avoid waiting the full 30s timer per test
- Navigate back to main menu via the "Back to Home" footer button
- Room selection in new tests picks randomly from all event rooms (not always index 0)

### Non-Goals
- No changes to application logic, components, CSS, or backend
- No changes to existing test scenarios 1–5
- No new API endpoints or WebSocket events

## Success Metrics

1. Test 6a renders "Connection Exchanged!" and navigates to `/` via "Back to Home"
2. Test 6b renders "Chat Complete" and navigates to `/` via "Back to Home"
3. Both tests pick a room at random from the available rooms (not fixed to index 0)
4. All 5 existing E2E tests still pass
5. No flaky failures from `page.clock` timer manipulation

## Technical Approach

- Two new test blocks in the existing `userFlow.spec.ts` describe block
- Match setup via API (same pattern as test #5): create event → join 2 users → select room → toggle available → poll for match
- Room selection uses `Math.floor(Math.random() * rooms.length)` to pick a random room from the full list, ensuring diverse room coverage across test runs
- Hydrate user context via `page.evaluate()` to set `localStorage` keys (`introchat_user_id`, `introchat_event_id`, `introchat_username`) so the ChatPage's `useUser()` hook has data
- Use `page.clock.install()` before navigation to install fake timers, then `page.clock.fastForward(31000)` to trigger the `onComplete` callback (CHAT_DURATION=30)
- Connection exchange: submit the *other* user's preference via API `request.post()`, then click the browser button for user A — the 2nd POST triggers the WebSocket broadcast
- Assert result text, click "Back to Home", assert URL `/`

### Architecture & Design Decisions

- **`page.clock` over real wait**: 30s real time × 2 tests = 1+ min. `page.clock.fastForward()` triggers all pending `setInterval` ticks instantly, cutting each test to ~5–10s.
- **API-driven match setup**: Reusing test #5's approach keeps tests fast and avoids navigating through the full join/save/room flow in the browser.
- **Random room selection**: `rooms[Math.floor(Math.random() * rooms.length)]` ensures each test run exercises a different room, improving coverage of the matching infrastructure across all 8 default rooms.
- **localStorage hydration**: Simpler than navigating through all preceding pages. Uses the same keys (`introchat_user_id`, `introchat_event_id`, `introchat_username`) as `UserContext`.
- **Separate events per test**: Each test creates its own event + users + match to avoid cross-test state pollution.
- **B submits via API, A clicks in browser**: The server requires both users to POST `/api/matches/{matchId}/connect` before broadcasting the result. We submit one via `request.post()`, the other via browser interaction.

## Open Questions & Risks

- **Risk: `page.clock` compatibility** — If Playwright 1.60's `page.clock.fastForward()` doesn't properly trigger React state updates from `setInterval` callbacks, fall back to real 30s wait with increased per-test timeout (90s). Mitigation: test locally first.
- **Risk: WebSocket timing** — The WebSocket event may arrive before React finishes processing the POST response. The `connection_exchanged`/`connection_declined` subscription should handle this regardless of ordering. If flaky, add a small `page.waitForTimeout(500)` after clicking.
- **Risk: localStorage hydration race** — The `UserProvider` reads localStorage on mount. Setting it before navigation should work, but if the page loads before `context` re-renders, the chat page may show "Back to Home" error. Mitigation: set localStorage before navigating to `/chat/...`.
- **Risk: Random room selection may cause rare failures** — If a specific room has a bug, random selection may surface it intermittently. This is desirable (improves coverage) but could be hard to reproduce. Mitigation: log the selected room name on failure.
