# PLAN_2026_06_02_051

## Problem Statement

When the user types in the "Add new room" or "Add new topic" input on the OrganizeEventPage, the selected/unselected state of default chips reverses — selected chips become ghost, unselected chips become solid. This happens on every keystroke.

## Goals & Non-Goals

### Goals
- Typing in any input on the page must never alter chip selection state
- Prevent stale closure race conditions in all state updaters
- Prevent StrictMode double-fetch from overwriting user toggles
- Add targeted tests covering toggle→type→stability scenarios

### Non-Goals
- No visual changes to the chip UI
- No backend changes
- No changes to other pages

## Success Metrics

- All 8 existing OrganizeEventPage tests still pass
- New chip-stability tests pass (toggle then type → state preserved)
- Full test suite passes
- Frontend builds without errors

## Technical Approach

### Root Causes

1. **Stale closures in state updaters** — `toggleRoom`, `toggleTopic`, `handleRoomClick`, `handleTopicClick`, `addRoom`, `addTopic` capture `rooms`/`topics` from the closure instead of using the functional updater pattern (`prev => prev.map(...)`). When React re-renders between a user toggle and the state flush, the outdated closure value is used, and a subsequent operation uses that stale value.

2. **StrictMode double-fetch race** — In development, React 18 StrictMode invokes the `useEffect` twice. If the second fetch completes AFTER the user has already toggled chips, `setRooms(data.rooms...)` overwrites the local toggle state with pristine backend data.

### Fixes

| Problem | Fix | Files |
|---------|-----|-------|
| Stale closures | Functional updaters: `setRooms(prev => prev.map(...))`, `setRooms(prev => prev.filter(...))`, `setRooms(prev => [...prev, ...])` | `OrganizeEventPage.tsx` |
| StrictMode race | Add `useRef` ignore guard to discard stale API responses | `OrganizeEventPage.tsx` |
| Missing coverage | Add chip-stability test file | `OrganizeEventPage.chip-stability.test.tsx` |
