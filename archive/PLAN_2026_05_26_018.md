# PLAN_2026_05_26_001

## Problem Statement

Buttons across all pages use inconsistent visual hierarchy: purple gradient (`btn-primary`) is used for primary CTAs despite unconventional color choice; green (`btn-chat`) is sometimes used for non-chat navigation actions and sometimes for chat actions; there is no clear tiered system distinguishing primary, secondary/affirmative, and tertiary/cancel actions. Users lack visual cues to guide them toward the most appropriate action on each page/section.

## Goals & Non-Goals

### Goals
- Establish a 3-tier visual hierarchy: Blue (primary CTA) > Green (affirmative/secondary) > Gray (tertiary/cancel/nav)
- Assign each button on every page to the correct tier based on context
- Rename `.btn-chat` → `.btn-affirmative` to match the new naming scheme
- Add QR icon to "Scan QR Code" button on HomePage
- Dynamic class switching on "Start Chat" button (accepted state): green when disabled alongside "I'm Ready", blue when both ready and sole CTA
- Ensure position-based + label-based accessibility (no sole reliance on color)

### Non-Goals
- No behavioral or logic changes to any page or component (except dynamic class on "Start Chat")
- No changes to non-button UI elements
- No responsive/mobile layout changes
- No analytics or tracking changes

## Success Metrics

1. Every page has exactly one Blue primary CTA per action section
2. No purple gradient remains in any button style
3. No `.btn-chat` class name remains in any file
4. All existing tests pass (Vitest, TypeScript, build)
5. "Start Chat" class toggles correctly: `.btn-affirmative` when disabled, `.btn-primary` when both ready

## Technical Approach

- Pure CSS class redefinition + class name changes in TSX files
- No new CSS classes introduced — only repurposing existing `.btn-primary` (blue gradient instead of purple) and renaming `.btn-chat` → `.btn-affirmative` (same green gradient)
- Dynamic class on "Start Chat" uses a ternary in the className prop: `className={yourReady && theirReady ? 'btn btn-primary' : 'btn btn-affirmative'}`
- QR icon: use emoji `🔳` or HTML entity — simplest approach without adding icon library dependency

### Architecture & Design Decisions

- **No icon library**: QR code icon will use emoji `🔳` to avoid adding a dependency
- **Dynamic class only on "Start Chat"**: This is the only button that shifts tiers based on state (disabled/sole CTA). All other buttons have a fixed tier.
- **Accessibility via position + labels**: Blue always appears first in action rows, Green second, Gray last. Labels are already distinct per action.
- **Color-blind safe**: Position hierarchy + distinct labels ensure usability without relying on color alone.

## Open Questions & Risks

- **Risk: Test references to `.btn-chat`** — if any test file (`.test.tsx`) references `.btn-chat`, it must be updated. Search for `.btn-chat` across all frontend source and test files during implementation.
- **Risk: Accessibility contrast** — Blue (`#3b82f6`) on white text should be checked against WCAG AA. Not blocking but flagged.
- **QR icon rendering**: Emoji rendering varies by OS. If emoji looks wrong, fall back to text-only approach.
- **Meta-task risk**: Changes to agent skills and AGENTS.md affect future interactions only. Verify the wording is precise enough that future agents follow the one-at-a-time rule without ambiguity.
