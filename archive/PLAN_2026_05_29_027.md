# PLAN_2026_05_29_001

## Problem Statement

The app currently has 4 pages (HomePage → UserInfoPage → RoomPage → ChatPage) but RoomPage bundles room selection AND nearby-people matching, while ChatPage bundles chat AND post-chat connection exchange. This makes the flow harder to follow and each page too broad in responsibility.

Goal: split into 6 clearly named pages matching the user journey — join → profile → room → people → chat → connect.

## Goals & Non-Goals

### Goals
- Split RoomPage: room selector stays, people+matching moves to PeoplePage
- Split ChatPage: chat experience stays, connection exchange moves to ConnectPage
- Update App.tsx with new routes and 6-step progress indicator
- Update all existing tests to pass with the new structure
- Update E2E tests to follow the new page flow
- Zero backend changes

### Non-Goals
- No new features or functionality
- No backend API changes
- No changes to existing components (ConnectionCard, Timer, etc.)
- No style/layout changes

## Success Metrics

- All 82 existing unit tests pass (updated to new structure)
- New PeoplePage.test.tsx and ConnectPage.test.tsx pass
- E2E tests pass with new routing flow
- `npm run typecheck` passes (no type errors)
- No runtime navigation regressions in the demo flow

## Technical Approach

Pure extraction: copy sub-views from RoomPage/ChatPage into new files, route to them, delete from originals.

### Routing Table

| Step | Route | Page | Source |
|------|-------|------|--------|
| Join | `/` | HomePage.tsx | Unchanged |
| Profile | `/join/:eventId` | UserInfoPage.tsx | Unchanged |
| Room | `/room/:eventId` | RoomPage.tsx | Room selector only |
| People | `/people/:eventId` | PeoplePage.tsx | Extracted from RoomPage |
| Chat | `/chat/:matchId` | ChatPage.tsx | Chat only (stripped) |
| Connect | `/connect/:matchId` | ConnectPage.tsx | Extracted from ChatPage |

### Data Flow

- RoomPage → PeoplePage: `navigate('/people/' + eventId, { state: { roomName } })`, read via `useLocation().state`
- PeoplePage → ChatPage: existing match ID logic (demo `createDemoMatchId()` or WS `match_found`)
- ChatPage → ConnectPage: `navigate('/connect/' + matchId)` on "End chat and connect"
- ConnectPage → back: "Start New Chat" → `/room/:eventId`; "Back to Home" → `/`

## Grill Outcomes

### Dimension: Assumptions
- Decision: RoomPage→PeoplePage data pass via React Router navigation state
- Rationale: Ephemeral data, no URL visible, no serialization needed
- Impact: PeoplePage reads room name from `useLocation().state`

### Dimension: Edge Cases
- Decision: Direct URL to `/people/:eventId` redirects to `/room/:eventId`. Direct URL to `/connect/:matchId` with invalid match shows error + back button.
- Rationale: Safe fallback for unexpected navigation; matches exist in-memory only
- Impact: PeoplePage has a guard useEffect; ConnectPage has error handling on fetch

### Dimension: Alternatives
- Decision: Skipped — separation is the explicit goal

### Dimension: Dependencies
- Decision: Low risk. Only App.tsx imports page components. RoomPage.test.tsx/ChatPage.test.tsx need updates but structure is preserved.
- Rationale: Pages are routed, not imported by other pages
- Impact: Clean split with no unintended coupling

### Dimension: Risks
- Decision: Low risk across all findings. Socket persists across routes (SocketContext above BrowserRouter). ConnectionCard is a pure component.
- Rationale: WebSocket connection lives in SocketContext at app root — not in individual pages
- Impact: ConnectPage can use socket subscriptions without reconnecting

### Dimension: Consistency
- Decision: All new pages follow same patterns as existing (named export, CSS wrapper, socket subscription cleanup via `unsub`)
- Rationale: Set by existing code conventions
- Impact: No style/pattern surprises

### Dimension: Code Discovery
- Decision: Skipped — graph confirmed all 4 existing pages and their communities
